# Phase 9 – Testing, Security & Deployment

Phase 9 makes CareerCraft safe to put on the internet and takes it live:

- **Security hardening:** login brute-force protection, a sign-up spam limit, stricter security headers, and production server settings.
- **Testing:** a security test suite on the backend, unit tests on the frontend, and CI that runs everything on every push.
- **Deployment:** backend in Docker on **Render** (or Railway), MySQL on **Aiven** (or Railway), frontend on **Vercel**.

> Phase 8 (Job Tracker) was skipped at your request. The sidebar still shows it as "coming soon", and it can be added later without changing anything here.

## 1. Security: what was added and why

| Risk | Protection | Where |
| --- | --- | --- |
| Password guessing | 5 wrong passwords for the same **email + IP** in 15 min → 429 + `Retry-After` header, even if the next password is right. A successful login resets the counter. Unknown emails count too, so attackers can't tell which emails exist. | `security/RateLimiter`, `security/AuthRateLimiter`, `AuthService` |
| One machine trying many accounts | 50 failures per IP in 15 min → 429 | same |
| Fake sign-up spam | 20 new accounts per IP per hour → 429 (configurable, e.g. raise it for a college lab behind one IP) | same |
| Locking out a real user | The key is IP **+** email, so an attacker elsewhere can't block you | same |
| Clickjacking, MIME sniffing, leaking URLs | API: `Content-Security-Policy: default-src 'none'`, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, `Permissions-Policy`, HSTS over HTTPS | `SecurityConfig` |
| XSS on the website | Vercel sends a strict CSP: scripts only from your own domain, no inline scripts, no `<object>`, no framing. Also React's escaping, plus server-side `http(s)://` validation of every link (tested: `javascript:` links → 400). | `frontend/vercel.json` |
| Wrong client IP behind proxies | Tomcat reads the real IP from trusted proxy headers. On Render it uses Cloudflare's `CF-Connecting-IP`, which visitors can't fake. | `application.yml`, `render.yaml` |
| Exposed source code | Production build has no source maps | `vite.config.js` |
| Secrets in images or the repo | `.dockerignore` and `.gitignore` exclude `.env` files. All secrets are environment variables. `JWT_SECRET` is generated by Render. | |
| Blank page on a crash | `ErrorBoundary` shows a friendly screen. After a new deploy it auto-reloads once if old page files are gone. | `components/common/ErrorBoundary.jsx` |

**Already in place from earlier phases (re-checked):** BCrypt(12) password hashes; stateless JWT with a ≥256-bit key (startup fails otherwise); every query scoped by user id, so another user's id returns 404; DTO validation and length limits on everything; uploads checked by type and size; errors never show stack traces; Grok key only on the server; AI prompt-injection guards and daily AI limits.

**Known trade-offs (fine for this project, worth knowing):**

- The JWT is stored in `localStorage`. The strict CSP above is the main defence. HttpOnly cookies would need CSRF protection and a same-site setup.
- Rate limits live in server memory. They reset on restart and aren't shared if you run several backend instances. With more than one instance, move them to Redis.
- Logout is client-side (tokens expire after `JWT_EXPIRATION_MS`, 24 h by default).

## 2. Production settings (`application.yml`)

| Setting | Why |
| --- | --- |
| `server.forward-headers-strategy: native` + `server.tomcat.remoteip.remote-ip-header` | Real client IP and `https` scheme behind the hosting proxy |
| `server.shutdown: graceful` | Redeploys finish in-flight requests (20 s max) |
| `server.compression` | Smaller JSON responses |
| `hikari.maximum-pool-size: 5` | Free MySQL plans allow few connections |
| `hikari.max-lifetime: 25 min` | Recycle connections before hosted MySQL drops idle ones |
| `app.security.*` | Rate limit numbers, all overridable via env vars |

New environment variables (all optional, defaults shown):

```
LOGIN_MAX_FAILURES=5
LOGIN_MAX_FAILURES_PER_IP=50
LOGIN_WINDOW_MINUTES=15
REGISTER_MAX_PER_HOUR=20
DB_POOL_SIZE=5
DB_MAX_LIFETIME_MS=1500000
REMOTE_IP_HEADER=x-forwarded-for     # cf-connecting-ip on Render
```

`GET /api/health` now also returns `clientIp`, the IP the server thinks you have. After deploying, open it and check that it shows your real public IP (see §6).

## 5. Deploy, step by step

You'll create three things: a **MySQL database**, the **backend** (Render) and the **frontend** (Vercel). Do them in this order, because each step needs a URL from the previous one.

### Step 0: Push the project to GitHub

```bash
cd careercraft
git init
git add .
git status          # make sure NO .env files are listed!
git commit -m "CareerCraft v1.0"
git branch -M main
git remote add origin https://github.com/<you>/careercraft.git
git push -u origin main
```

The **Actions** tab on GitHub now runs CI. Wait for the green check ✅.

### Step 1: MySQL database

Render doesn't host MySQL, so use a MySQL provider. Two easy options:

**Option A: Aiven (free plan, no credit card)**
1. Sign up at aiven.io → **Create service** → **MySQL** → **Free** plan → pick a region close to your backend (e.g. Singapore or Mumbai).
2. When it's running, open **Overview → Connection information** and note host, port, user (`avnadmin`), password, and database (`defaultdb`).
3. Your `DB_URL` is:
   ```
   jdbc:mysql://HOST:PORT/defaultdb?sslMode=REQUIRED&serverTimezone=UTC
   ```
   Aiven requires SSL, which `sslMode=REQUIRED` handles. The free plan has 1 GB of storage, and Aiven may power it off after a period of inactivity. You get an email and can power it back on.

**Option B: Railway MySQL** (usage-based pricing). In a Railway project, **New → Database → MySQL**. In its **Variables** tab, use `MYSQLHOST`, `MYSQLPORT`, `MYSQLDATABASE`, `MYSQLUSER`, and `MYSQLPASSWORD`:
```
jdbc:mysql://MYSQLHOST:MYSQLPORT/MYSQLDATABASE?useSSL=true&serverTimezone=UTC
```
Use the **public** host/port if the backend runs on Render, or the private ones if the backend also runs on Railway.

You don't need to create tables. The backend creates them on first start (`JPA_DDL_AUTO=update`).

### Step 2: Backend on Render

1. Render dashboard → **New → Blueprint** → connect your GitHub repo. Render finds `render.yaml`.
2. Fill in the values it asks for:

   | Variable | Value |
   | --- | --- |
   | `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` | from Step 1 |
   | `CORS_ALLOWED_ORIGINS` | `https://placeholder.vercel.app` for now (fixed in Step 4) |
   | `GROK_API_KEY` | your xAI key (or leave empty to run without AI) |

   `JWT_SECRET` is generated automatically. Don't change it later, or everyone gets logged out.
3. **Apply**. The first Docker build takes several minutes. When it shows **Live**, open
   `https://careercraft-backend-XXXX.onrender.com/api/health`. You should see `"status":"UP"`.

> **Free plan notes:** the free instance (0.1 CPU, 512 MB) spins down when idle, so the first request after a quiet period can take a minute or more while Java starts. The app shows "Cannot reach the server…" if that times out, and a retry works. For a portfolio you share with recruiters, a paid instance avoids cold starts.

**Alternative: backend on Railway.** New → **Deploy from GitHub repo** → in the service's **Settings**, set **Root Directory** to `backend` (Railway builds the `Dockerfile`) → add the same variables as above, plus a `JWT_SECRET` you generate with `openssl rand -base64 64` → **Networking → Generate Domain**. Leave `REMOTE_IP_HEADER` unset on Railway and check `/api/health` (§6).

### Step 3: Frontend on Vercel

1. vercel.com → **Add New → Project** → import the repo.
2. **Root Directory:** `frontend`. Vercel detects Vite, and `vercel.json` sets the build.
3. **Environment Variables:** `VITE_API_BASE_URL` = `https://careercraft-backend-XXXX.onrender.com/api` (your Render URL + `/api`, no trailing slash).
4. **Deploy.** Note your URL, e.g. `https://careercraft-asha.vercel.app`.

> `VITE_` variables are baked in at build time. If you change one, **redeploy**.

### Step 4: Connect the two

1. Render → your service → **Environment** → set `CORS_ALLOWED_ORIGINS` to your exact Vercel URL, e.g. `https://careercraft-asha.vercel.app` (no trailing slash; separate several URLs with commas, e.g. if you add a custom domain).
2. Save. Render redeploys automatically.

Vercel *preview* deployments get different URLs. They'll be blocked by CORS unless you add them, which is fine because previews are for checking the UI.

### Step 5: Smoke test

Open your Vercel URL, register, fill in your profile, create a resume, download the PDF, run an analysis, generate and publish a portfolio, and open `/p/your-name` in a private window. Use the go-live checklist below.

## 6. Go-live checklist

**Security**
- [ ] `git log --all -- '*.env'` shows nothing (no secret files were ever committed).
- [ ] The backend's `/api/health` shows **your** public IP in `clientIp` (compare with any "what is my IP" site). If it shows a `10.x`, `172.x` or Cloudflare address, set `REMOTE_IP_HEADER` as described in §2 and redeploy.
- [ ] Six wrong passwords in a row on the login page → "Too many failed login attempts. Try again in 15 minutes."
- [ ] Response headers on your Vercel site (DevTools → Network → document) include `content-security-policy` and `x-frame-options: DENY`.
- [ ] No CSP errors in the browser console while using the app (fonts, avatars and the API all load).
- [ ] `https://<backend>/api/users/me` without a token → 401 JSON.
- [ ] The frontend bundle doesn't contain your Grok key: DevTools → Sources → search for `xai-` finds nothing.

**Functionality**
- [ ] Register, log in, log out, and log in again.
- [ ] Profile photo upload shows the photo (served from the backend URL).
- [ ] Resume editor autosaves, and **Download PDF** works.
- [ ] Analyzer works with a key (or shows "AI not configured" without one).
- [ ] Portfolio publish works: `/p/<slug>` loads when opened **directly** in a new tab (this needs the Vercel rewrite).
- [ ] A refresh on any page (e.g. `/resumes/12`) doesn't 404.
- [ ] Test on a phone: layout, navigation drawer, and public portfolio.

**Operations**
- [ ] GitHub Actions is green on `main`.
- [ ] Database backups exist (both Aiven and Railway take automatic backups; check your plan).
- [ ] Optional: in Render → Settings, set **Auto-Deploy** to deploy only after CI checks pass.
- [ ] Optional, once stable: set `JPA_DDL_AUTO=validate` so Hibernate never changes the schema by itself (set it back to `update` temporarily if a future version adds columns).

## 7. Troubleshooting

| Problem | Fix |
| --- | --- |
| Frontend shows "Cannot reach the server…" | Backend asleep (free plan): wait a minute and retry. Otherwise check `VITE_API_BASE_URL` (must end in `/api`, `https://`) and redeploy Vercel. |
| Browser console: `blocked by CORS policy` | `CORS_ALLOWED_ORIGINS` must exactly match the site URL: `https`, no trailing slash, the production (not preview) URL. |
| Console: `VITE_API_BASE_URL is not set` | Add it in Vercel → Settings → Environment Variables, then redeploy. |
| Render deploy fails with `JWT_SECRET must…` | The secret is missing or too short. Let the Blueprint generate it, or use `openssl rand -base64 64`. |
| `Communications link failure` / `Access denied` in Render logs | Wrong `DB_URL`/user/password, the database is powered off (Aiven free), or SSL is missing: add `sslMode=REQUIRED`. |
| Too many connections | Lower `DB_POOL_SIZE` (e.g. 3). |
| `/p/my-name` gives Vercel 404 | `vercel.json` must be in `frontend/` and the project's Root Directory must be `frontend`. |
| Everyone gets "too many attempts" together | All users appear to have the same IP. Check `/api/health` and set `REMOTE_IP_HEADER` (`cf-connecting-ip` on Render). |
| Out of memory on Render free | Already capped at 75% of RAM. Upgrade the instance if you have many users. |
| Fonts or images blocked (CSP errors) | If you add a new external service (e.g. analytics), add its domain to the CSP in `vercel.json`. |
